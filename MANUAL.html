① Service Registry — Eureka

Padrão #1 do curso eureka-server:8761
💡 Feynman

Imagine uma lista telefônica automática. Cada serviço ao subir liga para o Eureka e diz "estou aqui, meu endereço é X". Quando o Gateway precisa chamar o course-service, pergunta ao Eureka "onde está o course-service?" em vez de ter o IP hardcoded. Se o serviço cair, o Eureka remove da lista em ~90s (heartbeat timeout).

Clientes: todos os serviços têm spring-cloud-starter-netflix-eureka-client e eureka.client.service-url.defaultZone nos configs do Config Server.

Por que self-preservation está desabilitado nesta POC

Com enable-self-preservation: false, o Eureka remove instâncias que param de enviar heartbeat imediatamente. Em produção isso fica habilitado para tolerar picos de rede — mas em POC local provoca o banner EMERGENCY confuso.

② API Gateway — Spring Cloud Gateway

Padrão #2 do curso api-gateway:8080
💡 Feynman

O Gateway é o segurança e recepcionista do prédio. Todo visitante (request) passa por ele. Ele valida o crachá (JWT), decide para qual andar (serviço) encaminhar, pode bloquear se o andar estiver sobrecarregado (Circuit Breaker) e conta quantas pessoas entram por minuto (Rate Limiter). ③ Circuit Breaker — Resilience4j

Padrão #3 do curso api-gateway + course-service
💡 Feynman

O disjuntor elétrico da sua casa: quando um aparelho começa a dar curto, o disjuntor desliga o circuito para proteger o resto. Em microsserviços, se o auth-user-service está respondendo em 10 segundos, o Circuit Breaker "abre" e retorna uma resposta de fallback imediatamente, sem fazer o cliente esperar — e sem derrubar o Gateway.

Estado FECHADO (normal): Gateway ──→ auth-user-service ──→ resposta OK Estado ABERTO (falhas ≥ 50% em sliding window de 10): Gateway ──→ [CB ABERTO] ──→ fallback imediato (503 + mensagem) ↑ Não chama o serviço! Espera 30s (waitDurationInOpenState) Tenta Half-Open: 1 chamada de teste Se OK → fecha. Se falha → abre novamente.

Configuração no Gateway

yaml — config-repo/api-gateway-dev.yml 
resilience4j.circuitbreaker:
  instances:
    authServiceCB:
      slidingWindowSize: 10
      failureRateThreshold: 50
      waitDurationInOpenState: 30s
      permittedNumberOfCallsInHalfOpenState: 3

Como forçar o Circuit Breaker a abrir

bash — parar auth-user e chamar rota protegida 
# 1. Para o auth-user (simula falha)
docker compose stop auth-user-service

# 2. Chama rota que depende de auth → deve retornar 503 + fallback
TOKEN="seu_jwt_aqui"
for i in {1..12}; do
  curl -s -H "Authorization: Bearer $TOKEN" http://localhost:8080/auth/users | head -c 100
  echo ""
done

# 3. Sobe o serviço de volta
docker compose start auth-user-service

Verificar estado do Circuit Breaker

curl -s http://localhost:8080/actuator/circuitbreakers | python3 -m json.tool
# Veja o campo "state": OPEN / CLOSED / HALF_OPEN

⑤ Saga por Coreografia — Matrícula em Curso

Padrão #5 do curso course-service → RabbitMQ → notification-service
💡 Feynman

Em uma dança coreografada, cada dançarino sabe sua parte e reage ao que o anterior fez — sem um diretor no palco. Na Saga Coreografia, cada serviço publica um evento quando termina sua parte, e o próximo serviço na cadeia consome esse evento e faz a sua parte. Não há orquestrador central.

Usuário │ POST /api/courses/{id}/enrollments ▼ course-service │ 1. Cria CourseUser (matrícula) no banco │ 2. Publica: enrollment.created → ms.courses.exchange ▼ RabbitMQ (Topic Exchange) │ routing key: enrollment.created ▼ notification-service │ 3. Consome evento │ 4. Cria Notification no banco │ 5. Publica: notification.sent → ms.notification.commands.exchange ▼ (course-service pode consumir confirmação se necessário)

Rollback (compensação)

Se a notification-service falhar 3 vezes (DLQ), a matrícula fica criada mas sem notificação. Em produção: implementar Consumer que lê a DLQ e publica enrollment.notification.failed, que o course-service consome para marcar a matrícula como NOTIFICATION_PENDING.

Como validar

bash — fluxo completo de matrícula 
# 1. Login (pegar JWT)
TOKEN=$(curl -s -X POST http://localhost:8080/auth/users/login \
  -H "Content-Type: application/json" \
  -d '{"username":"testuser","password":"Test@1234"}' | python3 -c "import sys,json; print(json.load(sys.stdin)['token'])")

# 2. Criar curso
COURSE_ID=$(curl -s -X POST http://localhost:8080/api/courses \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"name":"Spring Boot Avançado","description":"Curso completo","courseStatus":"ACTIVE","courseLevel":"ADVANCED","coursePrice":0.0}' | python3 -c "import sys,json; print(json.load(sys.stdin)['courseId'])")

echo "Course ID: $COURSE_ID"

# 3. Matricular usuário no curso
curl -s -X POST "http://localhost:8080/api/courses/$COURSE_ID/enrollments" \
  -H "Authorization: Bearer $TOKEN" | python3 -m json.tool
bash — verificar notificação criada pelo evento 
curl -s http://localhost:8080/api/notifications \
  -H "Authorization: Bearer $TOKEN" | python3 -m json.tool
No RabbitMQ Management (:15672) → queues, veja ms.notificationservice.enrollments.exchange — o contador de mensagens processadas deve subir.

⑥ Saga por Orquestração — Deleção de Usuário

Padrão #6 do curso auth-user-service (orquestrador)
💡 Feynman

Agora existe um maestro que coordena a orquestra. O auth-user-service sabe a sequência completa de passos para deletar um usuário e coordena cada serviço ativamente, aguardando confirmações. Se um passo falhar, o orquestrador aciona compensações em ordem reversa.

DELETE /auth/users/{id} │ ▼ ┌─────────────────────────────────────────┐ │ auth-user-service (ORQUESTRADOR) │ │ │ │ Step 1: Publica user.deleted │ │ → course-service consome │ │ → deleta enrollments do usuário │ │ → publica enrollments.cleared │ │ │ │ Step 2: Aguarda enrollments.cleared │ │ → notification-service consome │ │ → deleta notifications do usuário │ │ → publica notifications.cleared │ │ │ │ Step 3: Deleta usuário do banco │ └─────────────────────────────────────────┘

Como validar

# Deletar usuário (aciona saga orquestrada)
USER_ID="uuid-do-usuario"
curl -s -X DELETE "http://localhost:8080/auth/users/$USER_ID" \
  -H "Authorization: Bearer $TOKEN" -v

# Verificar que matrículas foram removidas no course-service
curl -s "http://localhost:8080/api/courses/$COURSE_ID/enrollments" \
  -H "Authorization: Bearer $TOKEN" | python3 -m json.tool

⑧ Event-Carried State Transfer — Réplica de UserData

Padrão #8 do curso auth-user → course-service (replica local)
💡 Feynman

Em vez de course-service chamar auth-user toda vez que precisa do nome do usuário, ele guarda uma cópia local do que precisa. Quando um usuário é criado ou atualizado, o evento carrega o estado completo (state transfer), não só "algo mudou". O course-service consome e atualiza sua tabela local user_data. Tradeoff: dado pode ficar brevemente desatualizado (eventual consistency).

auth-user-service course-service ────────────────────── ────────────────────── UserModel (source of truth) UserData (réplica local) ├── userId ├── userId (FK implícita) ├── username ──sync──→ ├── username ├── email ├── email └── fullName └── fullName Sincronização via evento user.created / user.updated Eventual consistency — máximo lag = tempo de processamento da fila

Código chave

java — UserEventConsumer.java (course-service) 
@RabbitListener(queues = "#{@courseUsersQueue.name}")
public void consumeUserCreated(UserEventDto event) {
    if (processedEventRepo.existsByEventId(event.eventId())) return; // idempotência
    var userData = new UserData(event.userId(), event.username(), event.email(), event.fullName());
    userDataRepository.save(userData);
    processedEventRepo.save(new ProcessedEvent(event.eventId()));
}

Verificar réplica no banco

SQL — course-service: verificar user_data replicada

  -c "SELECT user_id, username, email FROM user_data ORDER BY created_at DESC LIMIT 5;"

⑨ API Composition — Feign Client

Padrão #9 do curso course-service → auth-user-service via Feign

API Composition é o padrão onde um serviço agrega dados de outros serviços em uma única resposta. O course-service precisa mostrar dados do usuário junto com a matrícula — em vez de deixar o frontend fazer duas chamadas, o course-service chama o auth-user internamente via Feign (HTTP declarativo) e monta a resposta composta.

⑩ Log Aggregation — ELK Stack

Padrão #10 do curso Logstash + Elasticsearch + Kibana
💡 Feynman

Com 4 serviços, debugar um problema rastreando logs em terminais separados é impraticável. O ELK centraliza: cada serviço envia logs estruturados (JSON) via TCP para o Logstash → que processa e armazena no Elasticsearch → onde o Kibana permite buscar "todos os logs com traceId=X das últimas 2 horas em todos os serviços".

┌────────────┐ ┌────────────┐ ┌────────────┐ ┌────────────┐ │ auth-user │ │ course │ │notification│ │ gateway │ │ logback │ │ logback │ │ logback │ │ logback │ └─────┬──────┘ └─────┬──────┘ └─────┬──────┘ └─────┬──────┘ │ │ │ │ └──────────────┴──────────────┴──────────────┘ TCP JSON → Logstash :5001 │ ▼ Elasticsearch :9201 index: decoder-logs-{service}-{date} │ ▼ Kibana :5602 Discover → busca por service, traceId, level

🔐 JWT com JTI + Redis Blacklist

Melhoria arquitetural #1
💡 Feynman

JWT é stateless por natureza — o servidor não guarda tokens emitidos. O problema: como invalidar um token antes de expirar (logout, senha trocada, conta comprometida)? Solução: cada token recebe um ID único (JTI — JWT ID). No logout, o JTI vai para uma blacklist no Redis com TTL igual ao tempo restante do token. O Gateway consulta a blacklist em cada request.

Login → gera JWT com campo "jti": "uuid-único" Request normal: Client ──Bearer JWT──→ Gateway ──valida assinatura──→ Redis.get(jti) == null? ──→ OK Após logout: POST /auth/users/logout ──→ auth-user ──→ Redis.set(jti, "revoked", TTL=tempo_restante) Client ──Bearer JWT──→ Gateway ──Redis.get(jti) == "revoked"──→ 401 Unauthorized

Fluxo de logout

# Login
TOKEN=$(curl -s -X POST http://localhost:8080/auth/users/login \
  -H "Content-Type: application/json" \
  -d '{"username":"testuser","password":"Test@1234"}' | python3 -c "import sys,json; print(json.load(sys.stdin)['token'])")

# Chamar rota protegida — funciona
curl -s http://localhost:8080/auth/users \
  -H "Authorization: Bearer $TOKEN" | python3 -m json.tool

# Logout — invalida o JTI no Redis
curl -s -X POST http://localhost:8080/auth/users/logout \
  -H "Authorization: Bearer $TOKEN" -v

# Tentar novamente com mesmo token — deve retornar 401
curl -sv http://localhost:8080/auth/users \
  -H "Authorization: Bearer $TOKEN" 2>&1 | grep "< HTTP"

📤 Transactional Outbox Pattern

Melhoria arquitetural #2
💡 Feynman

Problema: você salva o usuário no banco e tenta publicar o evento no RabbitMQ. O banco salva mas o RabbitMQ cai — o evento se perde. O Outbox resolve: salva o evento na mesma transação do banco (tabela outbox_events). Um publisher em background lê o outbox e publica no RabbitMQ. Se o MQ falhar, o evento fica no outbox para reprocessar.

Transação Atômica (um único commit): ┌──────────────────────────────────────────┐ │ INSERT INTO users (...) │ │ INSERT INTO outbox_events ( │ │ event_type='user.created', │ │ payload='{"userId":...}', │ │ published=false │ │ ) │ └──────────────────────────────────────────┘ │ commit OK ▼ @Scheduled(5s): OutboxPublisher SELECT * FROM outbox_events WHERE published=false Para cada evento: RabbitMQ.publish(event) UPDATE outbox_events SET published=true WHERE id=?

Verificar tabela outbox

SQL — verificar eventos no outbox
docker exec -it decoder-poc-postgres-1 psql -U authuser -d authuser_db -c "
SELECT id, event_type, published, created_at
FROM outbox_events
ORDER BY created_at DESC
LIMIT 10;"
Eventos com published=false são "pendentes". Em circunstâncias normais, devem ser processados em ≤5 segundos (intervalo do @Scheduled).

🔁 Idempotência — processed_events

Melhoria arquitetural #3
💡 Feynman

O RabbitMQ pode entregar o mesmo evento mais de uma vez (at-least-once delivery). Sem controle, você cria duas matrículas para um enrollment.created duplicado. A solução: ao processar um evento, salve o eventId na tabela processed_events. Antes de processar, verifique se o ID já existe — se sim, ignore. É idempotente: pode receber N vezes, o efeito é sempre o mesmo.

SQL — verificar eventos processados (course-service)
docker exec -it decoder-poc-postgres-1 psql -U courseuser -d course_db -c "
SELECT event_id, processed_at
FROM processed_events
ORDER BY processed_at DESC
LIMIT 10;"

Teste de idempotência manual

# Publicar manualmente o mesmo evento duas vezes no RabbitMQ via Management API
# (simula redelivery do broker)
EVENT_PAYLOAD='{"eventId":"test-uuid-123","userId":"user-uuid","username":"testuser","email":"test@test.com","fullName":"Test"}'

# Publicar via RabbitMQ HTTP API
for i in {1..3}; do
  curl -s -u guest:guest -X POST http://localhost:15672/api/exchanges/%2F/ms.users.exchange/publish \
    -H "Content-Type: application/json" \
    -d "{\"properties\":{},\"routing_key\":\"user.created\",\"payload\":\"$EVENT_PAYLOAD\",\"payload_encoding\":\"string\"}"
  echo " (tentativa $i)"
done

# Verificar: deve ter só 1 entrada em processed_events com esse eventId
docker exec -it decoder-poc-postgres-1 psql -U courseuser -d course_db \
  -c "SELECT count(*) FROM processed_events WHERE event_id='test-uuid-123';"
# Esperado: count = 1

📊 CQRS Light — Interface Projections

Melhoria arquitetural #4
💡 Feynman

CQRS (Command Query Responsibility Segregation) separa leitura de escrita. A versão "light" usa Spring Data Interface Projections: ao invés de retornar a entidade completa (que pode ter campos sensíveis ou pesados), você define uma interface com só os campos que o endpoint precisa. A query SQL automaticamente faz SELECT só desses campos.

java — CourseListView.java (projeção de listagem) 
// Endpoint GET /courses → retorna só os campos de listagem
public interface CourseListView {
    UUID getCourseId();
    String getName();
    String getCourseStatus();
    String getCourseLevel();
    // NÃO inclui description, createdAt, updatedAt — não precisamos na lista
}

// Repository usa a projeção:
Page<CourseListView> findAllProjectedBy(Pageable pageable);

Diferença de payload

EndpointProjeçãoCampos retornados

🚦 Rate Limiting — Redis Token Bucket

Melhoria arquitetural #5
💡 Feynman

Imagine um balde com fichas. A cada request, você tira uma ficha. O balde se reenche a uma taxa fixa (replenish rate). Quando o balde está vazio, o próximo request recebe 429 Too Many Requests. No Spring Cloud Gateway, isso é implementado com Redis para ser consistente entre múltiplas instâncias do Gateway.

Configuração: replenishRate: 10 → 10 tokens adicionados por segundo burstCapacity: 20 → balde pode acumular até 20 tokens requestedTokens: 1 → cada request consome 1 token Resultado: 10 req/s em estado normal, bursts de até 20 req/s

Como forçar o rate limit

# Disparar 30 requests seguidos — os últimos devem retornar 429
for i in {1..30}; do
  STATUS=$(curl -s -o /dev/null -w "%{http_code}" \
    -H "Authorization: Bearer $TOKEN" \
    http://localhost:8080/api/courses)
  echo "Request $i: HTTP $STATUS"
done
Headers de resposta úteis: X-RateLimit-Remaining e X-RateLimit-Replenish-Rate indicam quantos tokens restam.

🔭 Distributed Tracing — Micrometer + Zipkin

Melhoria arquitetural #6
💡 Feynman

Uma request passa por Gateway → course-service → auth-user (Feign) → RabbitMQ → notification. Sem tracing, você não sabe onde a latência está. O Micrometer injeta um traceId na primeira entrada e propaga pelos serviços via headers HTTP e MDC de log. O Zipkin visualiza a árvore de spans completa com tempo de cada hop.

Request: GET /api/courses/{id}/enrollments traceId: abc123 Zipkin timeline: ├─ [Gateway] 0ms → 45ms (total span) │ ├─ [course-service] 2ms → 38ms │ │ └─ [Feign→auth] 5ms → 22ms ← latência aqui! │ └─ [RabbitMQ publish] 39ms → 44ms └─ [notification consumer] 50ms → 55ms (span assíncrono)

#!/bin/bash
set -e

  | python3 -m json.tool

echo -e "\n[2] Login → obter JWT..."
TOKEN=$(curl -sf -X POST "$BASE/auth/users/login" \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"Admin@1234"}' \
  | python3 -c "import sys,json; print(json.load(sys.stdin)['token'])")
echo "JWT obtido: ${TOKEN:0:40}..."

echo -e "\n[3] Criar curso..."
COURSE=$(curl -sf -X POST "$BASE/api/courses" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"name":"Decoder POC Course","description":"Todos os 10 padrões","courseStatus":"ACTIVE","courseLevel":"ADVANCED","coursePrice":0}')
COURSE_ID=$(echo $COURSE | python3 -c "import sys,json; print(json.load(sys.stdin)['courseId'])")
echo "Course ID: $COURSE_ID"

echo -e "\n[4] Matricular no curso (Saga Coreografia)..."
curl -sf -X POST "$BASE/api/courses/$COURSE_ID/enrollments" \
  -H "Authorization: Bearer $TOKEN" | python3 -m json.tool

echo -e "\n[5] Verificar notificação criada pelo evento..."
sleep 2
curl -sf "$BASE/api/notifications" \
  -H "Authorization: Bearer $TOKEN" | python3 -m json.tool

echo -e "\n[6] Verificar JWT blacklist (logout + reuso)..."
curl -sf -X POST "$BASE/auth/users/logout" \
  -H "Authorization: Bearer $TOKEN" -w "\nHTTP Logout: %{http_code}\n"
HTTP_CODE=$(curl -s -o /dev/null -w "%{http_code}" \
  "$BASE/auth/users" -H "Authorization: Bearer $TOKEN")
echo "Reuso do token após logout: HTTP $HTTP_CODE (esperado: 401)"

echo -e "\n[7] Verificar Eureka..."
curl -s http://localhost:8761/eureka/apps | grep -o '.*' | sed 's|<[^>]*>||g' | sort -u

echo -e "\n=== DEMO CONCLUIDO ==="
